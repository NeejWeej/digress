# What the model gets: context, prompts, skills, tools, the guide

Part of the notes for coding agents; [AGENTS.md](../AGENTS.md) has the overview and the index.

- **Context building:** `buildContext(tid, excludeMid, {tools})` returns `{system, messages, tools, docSeen}`. The system prompt includes the document (`docPreamble`): whole when it's under `DOC_BUDGET` (200k characters), with `[p. N]` labels. Branches get a prefix quoting the anchor (or, for a snip or page, an image of it). Keep the system prompt identical for every question in a conversation (nothing per-question in it), so all its threads share one prompt cache.
- **Images in context:** `buildContext` emits `{type:'image', ref}` parts; `resolveContext` turns them into bytes right before sending and fails the whole request if one can't be loaded (never send with a piece missing). Connectors without `supportsImages` get a visible note in place of each image. `tests/test_context.py` checks that every message and image on a branch's path reaches each provider intact; keep it passing.
- **Document tools** (`server/doctools.mjs`, `runDocTool` in the client): `search`, `read_pages`, `view_page`, defined once on the server and run in the browser (it has the PDF open). `search` takes `queries` (up to `SEARCH_MAXQ`, one call from the budget; the old `query` still works): each is matched on folded text (`foldText`: case, accents, ligatures, and spaces, hyphens, dashes and quotes left out, so a word hyphenated across a line matches; a match starts at a word), and one not found that way gets the closest passages (`nearPassages`: windows of `SEARCH_WIN` words, BM25-style, words that start the same count, marked as not exact). The folded pages are kept on `docState` (`docFold`). `tests/test_doc_search.py`. Each reply's tools are the ones the page names (`buildContext`'s `tools`, a list of names; the session's `s.tools`, which `toolsForAnthropic(s)`, `toolsForOpenAI(s)`, `claudeCodeToolNames(s)`, Gemini's `toolDecls(s)` and the MCP `tools/list` spell). **`suggest_card`** (`CARD_TOOL`) is offered in every request of a conversation with flashcards on (`cardTool`), replies and side jobs alike so they share one prompt cache, but only a reply runs it (`suggestCard`: into the inbox, `src:'suggested'`, `at` the reply, a repeated front refused, refused when cards are off; `generate` toasts the count); `runDocTool` refuses it for drafting, takeaways and fixes. Its calls have their own limit (`MAX_CARD_CALLS`), apart from the document budget. `tests/test_suggest_card.py`; the fake page server runs tools when a test sets `window.fakeTools` (`opts.callTool`). The server sends each call down the reply's stream as `{tool:{id,name,input}}`; the page posts the result to `/api/chat/tool` `{chat,id,parts|error}`, where `session.call` is waiting. The agentic loop is per provider: `chatViaApi` and `chatgpt.chat` loop while the model stops on tool calls; Claude Code runs its own loop against a one-reply MCP endpoint (`/api/mcp/<token>`). Every failure goes back to the model as readable error text, never an empty result; `MAX_TOOL_CALLS` (30) per answer, stated up front in every tool description and counted down in results once 3 or fewer are left, and `MAX_TOOL_ROUNDS` requests per answer for every provider (Claude Code: `--max-turns`, whose `error_max_turns` is shown as readable text). A model still calling tools at `MAX_TOOL_ROUNDS` gets one more request with `tool_choice` none (`final`), so it answers from what it read; and the page never saves a reply with no text as finished (it becomes an error with Retry). This once ended a reply silently empty. For a document over the budget, the model starts from its table of contents (`pdfOutline`) and the first `DOC_FIRST` pages; a branch about a passage carries that page ±1 in its first message (`aroundParts`). Card drafting and takeaways use the same context and tools as the conversation (same system prompt, so they share its cache); `{tools:false}` gives the old page-picking preamble with gap markers, used when a connection has no tools. `tests/test_doc_tools.py` drives every provider through the same scripted session (`tests/fakes/doc-script.mjs`).
- **Prompts, skills & tools** (`#promptsBtn`, the sliders icon beside Activity → `openPrompts`, `#promptsPage`, a page like Activity, in `closeTopmost`): the system prompt has two parts: `PROMPTS.system`, who the tutor is and how it writes, which the reader can replace, and `PROMPTS.howDigress`, how the app works (formatting the page can draw, the web rule, the fork rule: a `[Side question …]` message is where a branch forks and everything after it is in that branch, and what the model can't see), always sent after it (`fullSys(c)`: `sysPrompt(c)` + `howDigress` + `skillsPrompt(c)`), shown read-only (`.pphow`). Anything the app relies on goes in `howDigress`, never in `system`, so a reader's prompt can't drop it. A side branch is marked only where it forks, never on each question: the path is linear, so the rule says it. **What the model sees** (`showModelView`, the last row of `#skillMenu`, `data-sk="?"`): a debug dialog with the request the next question in `pickerTid()` sends (`buildContext`, `lastDocSeen` kept), its tools, the system prompt by part and every message with its markers, and Copy as JSON. The reader's own default system prompt and quick questions are in `CUSTOM.prompts` (the store's `prompts/custom`, `{system?, quick?}`, only what differs from `web/prompts.js`; `defaultSys()`, `quickList()`; `fillPopChips` redraws the popup's chips). A conversation can have its own, `conv.system` (only when it differs from the default; `sysPrompt(c)` is it, else `defaultSys()`; `setConvSystem`), set before the first question from the empty main pane (`convSysBox`, a `.csys` whose textarea exists only while it's open, since tests find the composer as the pane's textarea) or later from the top bar (`editConvSystem`, a `#modal` dialog with `#cSysEd`); it makes the conversation not `isBlank`. It's every thread's, document branches included, so in a document conversation the empty main pane's box is where it's set for them even if main is never used (`sysScope` says so in the box and the dialog). The top bar's `#skillT` (labelled Prompt, Own prompt or the skills that are on) always opens `#skillMenu` (the system prompt row, then Skills, with a `.sknone` line when there are none, then Prompts, skills & tools… and What the model sees here…; Esc closes it). No skills come with Digress: the section starts empty. The Tools section (`renderToolList`, `TOOL_INFO`: a table of what turns each on, the model's descriptions folded; `io.llm.toolList` → `GET /api/tools`) is read-only. Skills are `CUSTOM.skills` (the store's `skills`, `{id, name, description, body, text, source}`; `parseSkill` reads the SKILL.md header, `putSkill`, `skillFromLink` through `io.files.fromLink`, with GitHub folder/file pages turned into raw URLs by `skillLink`). Both are loaded once at startup (`loadCustom`, in `initConnectors`, before anything is asked). A conversation turns skills on with `conv.skills` (ids; the top bar's `#skillT` → `openSkillMenu`/`toggleSkill`; `syncSkillT`), and `buildContext` puts `skillsPrompt(conv)` (`PROMPTS.skills`) right after the conversation's system prompt and before the document: the same for every thread of the conversation, so the prompt cache stays shared. A skill applies to a whole conversation: changing the system prompt per thread would split the cache (per-thread skills would need every skill on in the system prompt and a mark on each question saying which apply, the way `PROMPTS.webOn` works). The rest of `PROMPTS` is shown read-only (the code parses what they ask for). `tests/test_prompts_skills.py`.
- **Ask about Digress** (`#guideB`, the ? beside How it works; `askGuide`, `PROMPTS.guide`): a one-off chat with `GET /api/guide`'s files in its system prompt, kept only in page memory (`GUIDE`), never saved or added to a conversation. **It answers from README.md and the docs, so keep them current when a feature changes:** a feature missing from them is one it will say doesn't exist. `tests/test_guide.py`.
