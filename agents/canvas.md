# The canvas

Part of the notes for coding agents; [AGENTS.md](../AGENTS.md) has the overview and the index.

- **The document pane can live on the canvas.** When the document's card is docked (`S.dock.doc`, via Expand or snapping it to an edge) and the canvas is showing, the real `paneEls.get('doc')` element is moved into that card (`placeDocPane`, after every `renderCanvas` and `layout`); `layout()` skips it meanwhile (`docInDock`), and switching back to Columns/Rows puts it back. Expand (`docdock`) fills the canvas (`REGIONS.fill`); dragging to a side edge or **Side** (`docside`) docks it to half; a branch marker followed from the filled document moves it to the side first. Clicks inside it go to the pane's own handlers, except branch markers, which go to their cards. Don't clone the pane or render the PDF a second time. Moving the element resets its scroll (a reader on p. 95 landed on p. 1), so where you are is kept as a mark-like spot as you scroll (`noteDocSpot`, `docView.spot`) and put back after each move and after the PDF is laid out again at a new width (`putDocSpot`): one spot shared by both views. `tests/test_canvas_doc.py`, `tests/test_doc_view_spot.py`. A PDF is never laid out at a hidden or moving pane's zero width (`buildPdfPages` sets `docView.stale` instead, and the resize watcher redraws once the pane has a width): it once came out at the 260px minimum and stayed there, docked on the canvas on a slow machine. A text document re-wraps the moment its width changes (a pane closed, the sidebar hidden), so the doc pane's ResizeObserver puts the spot back at once (`pb.__tw`); a PDF does it after it's redrawn. `tests/test_doc_text_reflow.py`. Thread panes do the same (`paneRO`, `notePaneSpot`/`paneSpotNow`/`putPaneSpot`): the exact character at the reading line (`caretAt`/`charRect`; else the message, the block in it and how far into it; or `bottom`), measured from the top of the pane, not of its `.pb` (a narrow pane's header wraps, and unwraps when it widens), unless something jumped the pane elsewhere since its spot was noted (a nudge from the browser's own scroll anchoring still counts as the same place). `tests/test_pane_keep_place.py` (at iPad size, with Chrome's scroll anchoring off, as Safari has none). `renderPane` keeps the scroll offset across its redraw and notes the spot again in the rebuilt message: without that, opening a branch (which redraws the reply it's on, then narrows the pane) jumped the parent up by a screenful; `tests/test_side_question_keeps_place.py`.
- **Canvas coordinates:** cards have world positions; the camera scale is `cam.k`, and each card has its own zoom (CSS `zoom` via `--cz`). Stored sizes are at 100%. Anything that converts screen ↔ content uses `contentScale(node)` (which is 1 for cards stuck to the screen). Scroll offsets inside a zoomed card must be divided by it.
- **Columns → canvas** (`setView` → `cvArrive`): the card for the pane last clicked, typed in or scrolled (`lastPane`, else the pane most in view) flashes; the camera pans only if its title bar is off screen. Look only: it never folds, unfolds, expands or saves (don't swap in `focusCard`, which does). `tests/test_canvas_arrive.py`. The card then stays marked (`cvHere`, `.here`, `#cvHereTag`) for the whole canvas visit (cleared by switching to Columns/Rows or another conversation); while it's marked, `#zHere` in the canvas toolbar glides back to it (`panToCard`).
- **Canvas drags own their press** (`cvTake`): panning, moving or resizing a card turns text selection off for the whole page until the press ends (`.cvnosel`) and sets `cvTook`, so `checkSelection` opens no branch popup from text the drag swept over (the docked document, a card). A card brought into view (`panToCard`, `focusCard`, `cvArrive`) is centred in `cvFree()`, the part of the canvas not covered by docked cards. In the docked document, the pane-only buttons (reorder grip, Collapse, Collapse others) are hidden. `tests/test_canvas_doc.py`.
- **Jumping to where a branch came from, on the canvas** (`canvasRevealSource`, from the branch card's `.cq` line; a whole-reply branch's line says "The whole reply"): a docked document is the real pane, so it uses `revealDocAnchor` and the pane's own Return. A thread card (main or any branch) remembers where it was being read in `cvPrev` (per conversation and card, outside the element, since `renderCanvas` rebuilds cards) and shows Return (`.cjp` in its `.cjump`, `.hasprev`). `tests/test_canvas_return.py`.
- **Branch chips** (`branchChips`): under each reply, a chip per branch off it (`shownOn`), in a pane (`buildFoot`) and in an open canvas card (`canvasMsgEl`), outside `.body` so anchors are unaffected. It's the only way into a branch about the whole reply, which has no inline marker; on the canvas a chip goes to the branch's card (`focusCard`) and its line starts there (`drawEdges`). `tests/test_canvas_whole_branch.py`.
- **Long threads' cards** (`renderCanvas`): a card that isn't expanded lists every message only up to `CARD_ROWS_ALL` (8); past that it keeps the first and last exchanges and every message a branch comes off with the question before it (the lines between cards start at those rows, so they must stay), and each run in between is a `.cr.gap` row ("⋯ N more messages", `data-cmid` the first hidden one) that expands the card there. `tests/test_canvas_long_card.py`. An expanded card's replies have the pane's line under them (`canvasMsgEl` → `buildFoot`: Side question, Copy, ⋯, Redo/Retry/Continue, model, context, chips; plus the error, web sources, doc reads), and both go through `replyAct`, so anything new under a reply works in both; `tests/test_canvas_reply_foot.py`.
- **Canvas views** copy on load: `useView` puts a view's `cv` and camera onto this device's canvas; only Update writes back. `tests/test_views.py`.
