# Search

Part of the notes for coding agents; [AGENTS.md](../AGENTS.md) has the overview and the index.

- **Search index = passages.** `indexEntries` splits every message and document page into ~900-character passages (`passages()`: paragraphs, code fences kept whole, a ~120-character overlap with the passage before, `o` = its length), with nothing cut off; results are one row per message (its best passage), ranked exact phrase first, then more typed words as typed, then BM25. `IDXV` is the index format: bump it when entries change shape, and older indexes are rebuilt by `idxBackfill`. Document pages are rebuilt from the index with `idxPages` when the document isn't loaded. `tests/test_search_passages.py`, `tests/test_search_phrase.py`.
- **Two search engines.** With the real server (`/api/health` says `search:true`), `io.index.search` asks `GET /api/search` and `server/db.mjs` (`searchPassages`: SQLite FTS5) finds *and orders* the results; `queryIndex` returns them as they come. Without it (the demo, and `tests/fakes/page-server.js`, which every `goto_app` UI test uses) the page runs MiniSearch with the rules in `web/js/searchrank.js` (`MS_OPTIONS`, `rankHits`, `searchMini`, `KIND`). The ranking itself is one piece of code: `searchPassages` imports `KIND` and `rankHits` from `searchrank.js` (the phrase-then-typed-words-then-BM25 sort, the boost per kind, `qWords`: folded, one-letter words don't count), each engine supplying its own BM25 `score`. What's still written twice is finding the results: the last word as a prefix, typo tolerance for 5+ letter words, and accent folding (FTS5's `unicode61 remove_diacritics 2`; `foldTerm` as MiniSearch's `processTerm`: café = cafe). Highlighting compares folded words with `foldKeep(text)`, which folds without moving any character, so an offset found there is the offset in the text (`matchTerms`, `bestSpot`, `snippet`, `showHit`, `passageAt`'s callers). They can't be identical (word splitting differs at the edges; typos are an edit-distance pass over `fts5vocab` on the server, MiniSearch's `fuzzy: 0.2` in the page; scores are on different scales, so a BM25 tie-break can go either way), so what's held equal is which results come back and their *tiers*: results grouped by `(phrase, exact)`, the rules we wrote, in the same sequence with the same members; order inside a tier isn't compared. **Change how one engine finds results, change the other**, and run `tests/test_search_parity.py` (→ `tests/search_parity.mjs`: the same conversations indexed by `indexEntries`, put through both engines, query by query; it also fails if `db.mjs` grows a ranking of its own again). The `test_search*.py` UI tests only ever see MiniSearch; the server's side is `tests/server_unit.mjs` and `test_server.py`. Each index put replaces the conversation's passages by diff (`syncPassages`: rows compared on every stored field, unchanged ones kept), so a save in a long conversation doesn't re-add every FTS5 row.
- **Search scope:** `PAL.scope` is `all` | `conv` | `thread` (`PAL.stid`: the pane last used, `lastPane`, or the one whose magnifier `data-act=jsearch` opened it; `'doc'` = document pages). Filtering happens after ranking, in `searchNow`; Tab cycles the chips. `tests/test_search_scope.py`.
- **"Describe it instead"** (`findExpand`, `findPick`; prompts in `PROMPTS.find`): one-off model calls with its own model (`findModel`: `settings.findModel`, picked in its row with `findModelButton`, the model menu in `find` mode via `openModelMenu`; by default `fastModel`, never a Gemini one unless that's all there is), never added to a conversation or saved. Step 1 sends only the typed description and the titles in the search's scope (`scopeTitles`), never message text; its phrases are searched as usual and merged, and each result keeps the phrase that found it (`r.q`, used for its preview and landing). Step 2 runs only when chosen and sends ~300-character snippets of the top 25 candidates. Hidden offline or without a model. `tests/test_search_describe.py`.
- **Search landing and Back:** `openResult` → `showHit` finds the result's passage in the rendered message (`passageAt`, a run of its words that occurs once), then the typed phrase or the closest cluster of searched words in it (`bestSpot`) and paints them with the CSS Highlight API (`CSS.highlights` `digress-hit`): no DOM changes, so anchors are untouched. `markBack` snapshots the view (conversation, open panes, scroll, camera) once per search (and before a pinned branch opens); the `#backChip` (in the top bar, so it never covers a pane's buttons) pops it (`goBack`); opening a conversation yourself (sidebar, New) clears it. `tests/test_search_jump.py`.
